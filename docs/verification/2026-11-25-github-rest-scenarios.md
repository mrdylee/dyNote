# 개인 노트 GitHub REST 동기화 검증

기준 버전은 Windows x64 시험판 `v0.23.22-beta.2`의 커밋 `4f3a3b5`다. 아래 시나리오는 개인 보관함의 브라우저 로그인, 저장소 선택, 송수신 및 재시작을 다룬다.

인증·전송 자동 테스트를 21개에서 66개로 확대했다. 같은 66개를 기준 버전의 코드에 실행하면 50개 통과, 16개 실패였고, 수정 후에는 66개 모두 통과했다. 재시작 테스트는 설정 파일 쓰기 실패와 네트워크 응답 유실을 주입한 뒤 보관함을 다시 열어 실제 파일을 비교한다. 물리 기기의 갑작스러운 전원 차단은 시험 범위 밖이다.

수정본 `cc8bc9d`에서 집중 테스트 66개를 10회 반복해 모두 통과했다. 전체 680개 중 Mac은 678개 통과·2개 건너뜀, Windows x64는 676개 통과·4개 건너뜀으로 두 환경 모두 실패 0개였다. Mac에서 건너뛴 2개는 Windows 전용이며, Windows에서 건너뛴 4개는 파일 권한과 모드에 의존하는 테스트다. 두 환경의 Electron에서 로그인 거절·취소·재시도, 역순 새로고침, 저장소 선택, 첫 수신과 연결 해제를 확인했다. ## 실행 방법

저장소 루트에서 `node --test tests/github-login.test.mjs tests/github-api-sync.test.mjs`를 실행한다. 두 테스트 파일은 가상 GitHub 응답을 사용한다. 파일 읽기·쓰기, 보관함 재시작, 동기화 판단은 실제 앱 코드를 실행한다. 전체 자동 테스트는 `npm test`로 실행한다. [인증 테스트](../../tests/github-login.test.mjs) · [보관함과 전송 테스트](../../tests/github-api-sync.test.mjs)

Windows에서는 **Build Windows distribution** 작업이 패키징한 Dynote를 실행한다. GitHub 응답을 제어해 로그인 거부·취소·재시도와 역순 새로고침을 확인한 뒤 보관함에서 받은 노트를 읽는다. 기존 설치 업데이트 검증에서는 이전 시험판을 설치한 뒤 앱 내 업데이트와 재실행을 거쳐 기존 노트와 설정을 확인한다. [Electron 시나리오](../../scripts/verify-github-login-ui.mjs) · [Windows 작업](../../.github/workflows/build-windows-distribution.yml)

첫 Windows 실행은 문서 편집기 설치 준비 단계에서 시간 제한에 도달했다. 같은 소스의 두 번째 실행에서 `v0.23.22-beta.1` 사용 중 앱 내 업데이트로 이번 빌드를 설치했고, 재실행·재설치 후 기존 노트와 설정이 유지되는 것을 확인했다. Windows x64 설치 파일과 ZIP도 업로드됐다. [설치 검증과 결과물](https://github.com/mrdylee/dyNote/actions/runs/45631058388/attempts/2)

## 로컬 파일 확인 속도

`node scripts/benchmark-github-note-scan.mjs`는 임시 폴더에 4 KiB 노트를 100개와 1,000개 만들고, REST 동기화가 로컬 변경을 찾는 데 걸린 시간을 각각 5회 밀리초로 기록한다. 각 회차마다 앱의 파일 해시 캐시가 비어 있을 때, 변경이 없을 때, 한 파일만 편집했을 때를 측정한다. 운영체제의 디스크 캐시는 유지한다. 네트워크와 자동 확인 대기 시간은 측정 범위 밖이다. Windows 수동 빌드의 `Measure local GitHub API note scan time` 단계에서도 같은 수치를 확인할 수 있다. [측정 스크립트](../../scripts/benchmark-github-note-scan.mjs)

이 Mac에서 노트 1,000개를 검사한 중앙값은 해시 캐시를 처음 채울 때 126 ms, 변경이 없을 때 12 ms, 한 파일을 고쳤을 때 12 ms였다. 두 방식 모두 자동 원격 확인 간격은 55~60초이고, 기존 Git 방식은 자동 전송 시 편집을 최대 약 5분간 묶는다. **지금 동기화**로 측정한 수동 전송 시간에는 이 대기가 들어가지 않는다. [자동 확인 간격](../../electron/git-controller.mjs) · [Git 묶음 전송](../../core/personal-sync.mjs)

같은 가상 노트와 실제 GitHub로 Git과 REST의 저장·송수신 시간도 각각 6회씩 비교했다. [48회 전송 속도 비교와 원자료](2026-11-25-github-sync-speed.md)

## 실제 GitHub 전송

별도로 가상 노트 전용 비공개 GitHub 저장소와 Mac의 임시 보관함 세 개를 사용했다. 기존 GitHub CLI 로그인으로 REST 요청을 인증했다. 테스트가 생성한 파일만 수정하거나 삭제했으며, 시작 전부터 있던 파일은 경로·모드·Git 해시를 대조했다.

배포 기준 코드에서 한글·공백 경로, 2,092바이트 WAV, 오프라인 편집, 동일 노트 충돌, 서로 다른 노트 편집, 이름 변경, 삭제, 변경 없는 재확인까지 8개 시나리오를 통과했다. 마지막에는 원격과 세 폴더의 21개 파일이 일치했고, 변경 없는 재확인 6회에서 쓰기 요청은 0건이었다.

수정본 `cc8bc9d`로 같은 8개를 다시 실행했다. 기존 21개 파일을 그대로 보존했고, 시험이 끝났을 때 총 27개의 경로와 내용이 세 보관함과 원격에서 일치했다. 변경 없는 재확인 6회는 브랜치 조회 6건으로 끝났다.

같은 시나리오를 데스크톱 앱으로 재현하는 순서다.

1. A·B·C의 빈 개인 노트 폴더를 같은 테스트 저장소에 연결한다. A에서 테스트 폴더와 공통 노트, 한글 이름의 첨부를 만들고 B와 C에서 받는다.
2. B의 네트워크 연결을 끊고 공통 노트를 편집한다. A에서도 같은 노트를 다르게 편집한다. A와 B에서 서로 다른 새 노트를 하나씩 만들고 A에서 동기화한 뒤 B를 다시 연결한다.
3. 세 곳에서 **지금 동기화**를 누른다. 공통 노트의 두 편집본, 서로 다른 두 새 노트, 원본과 같은 해시의 첨부가 모두 있어야 한다.
4. C에서 테스트 파일 하나의 이름을 바꾸고 A와 B에서 받은 뒤, A에서 그 파일을 삭제해 다시 동기화한다. 세 곳에서 이전 이름과 새 이름이 모두 사라지는지 확인한다. 추가 편집 없이 다시 동기화했을 때 GitHub 커밋 수가 그대로여야 한다.
