# 개인·팀 노트의 즉시 동기화와 복구

## Windows x64 미리보기 4에서 사용하는 방법

왼쪽 **개인 노트** 또는 원하는 **팀 공유 노트** 제목·폴더·파일·빈 영역을 우클릭해 **지금 동기화**를 누른다. 해당 보관함의 열린 편집을 먼저 저장하고, 원격 변경을 받아서 내 변경을 올린다. 결과는 우클릭한 패널의 제목 아래에 표시된다. 이 메시지를 누르면 해당 보관함의 상세 화면이 열린다.

- **개인 노트**는 기존 기기 등록과 파일 버전 보호를 사용한다. 미설정 보관함은 **동기화 설정…**에서 시작한다. 복사 직후의 PDF·ZIP·Office 파일은 수동 동기화 중 안정성 검사 시간(1.5초)을 두고 한 번 더 확인한다. 복사 중인 파일은 대기 목록에서 확인한다.
- **팀 노트**는 선택한 팀 저장소의 브랜치를 사용한다. 팀별로 등록한 저장소는 일일 백업을 먼저 켤 필요 없이 수동 동기화할 수 있다. 서로 다른 편집은 Git이 안전하게 합칠 수 있을 때 반영한다. 충돌하거나 직접 스테이징한 변경이 있으면 패널에서 사유를 확인하고, 변경을 정리한 뒤 다시 누른다. 저장소 연결이 필요한 팀은 팀 저장소 설정으로 이동한다.
- **파일이 도착하지 않을 때**는 상세 화면에서 **이 PC에만 있는 항목**을 열어 파일 형식과 Git 제외 규칙을 확인한다. 개인 보관함은 전송 대기 사유, 마지막 원격 확인 시각, 마지막으로 확인된 업로드 시각도 표시한다. 일시적인 연결 오류는 자동 재시도하고, 권한·기기 기록처럼 조치가 필요한 오류는 **진단 복사**로 확인할 수 있다.
- **Cloud PC의 기기 등록 JSON**은 원래 등록 필드가 모두 일치하는 줄바꿈·UTF-8 BOM·들여쓰기 차이를 처리한다. 기기 이름·등록 상태 등 실제 값이 바뀌면 파일을 보존하고 확인할 필드를 알려 준다.
- **공유 폴더에서 파일 교체에 실패했을 때**는 수신 원본을 기존 위치에 복구한다. 다른 파일이 먼저 생겨 그 위치를 사용할 수 없다면 설정의 **복구 사본 위치 열기**로 원본을 찾을 수 있다. 저장 위치가 필요한 파일 작업을 지원하는지는 수신 전에 검사한다.

현장 확인은 두 PC의 개인 보관함에서 작은 Markdown 파일을 왕복하고, 팀 패널에서도 같은 방식으로 해당 팀의 파일 한 개를 주고받는다. 각 PC에서 수신한 본문과 원격 브랜치를 확인한다. 회사 VDI의 실제 NAS에서는 파일 열기·교체·재연결 시험이 남아 있다.

## 미리보기 4 검증 결과

전체 회귀 테스트는 macOS에서 593개가 통과했다. Windows 전용 설치 도우미 테스트 1개는 건너뛰었다. Windows x64 ZIP의 CRC와 실행 파일을 확인하고, 패키지의 소스·렌더러 빌드 파일 310개를 대조했다.

- 독립 Electron 프로필 3개와 임시 Git 원격에서 개인 패널의 우클릭, 편집 중인 노트 저장, 양방향 전송, 같은 문장의 충돌 해결을 확인했다. 서버가 쓰기를 거부한 동안의 편집도 권한 복구 후 전송됐다.
- 개인 저장소와 팀 저장소 3개를 함께 연 뒤, 한 팀의 `notes` 브랜치에서 동료의 노트를 받고 로컬 노트를 올렸다. 다른 팀과 개인 저장소의 커밋은 유지됐고, 선택한 팀의 상세 화면에는 업로드에서 제외된 파일과 이유가 표시됐다.
- `core.autocrlf=true`인 Git 복제본에서 편집하지 않은 Markdown·PDF가 새 팀 커밋을 만들지 않았고 수정한 PDF는 바이트 그대로 올라갔다. 공유 폴더의 파일 교체 실패는 오류를 주입해 재현했다. 다른 파일이 원래 위치를 차지한 뒤 재시작 검사까지 실패한 경우에도 이전 파일의 복구 사본을 찾을 수 있었다.

## 미리보기 3에서 재현한 증상과 당시 복구 방법

이하 내용은 2026-11-24에 미리보기 3(0.23.19)의 동기화 코드를 macOS의 독립 보관함 두 개와 임시 Git 원격 저장소에서 검토한 기록이다.

| 보이는 현상 | 지금 할 일 |
| --- | --- |
| `동기화됨`인데 파일 하나가 없다 | 보낸 PC에서 확장자·크기와 파일별 대기 사유를 확인한다. 새 `.docx`는 개인 동기화 대상에서 제외된다. 원본을 전달해야 한다면 문서를 담은 25 MiB 이하 ZIP을 `File Storage`에 넣을 수 있다. `복사 완료 대기`는 복사가 끝난 뒤 다시 동기화한다. |
| 두 PC에서 같은 노트를 고쳐 `버전 확인`이 뜬다 | 해당 파일의 **버전 확인**을 열어 양쪽 내용을 비교한다. Markdown에서 겹친 문장은 남길 내용을 선택한다. 첨부 파일 두 개를 보존하려면 버전을 고르고 **모두 유지**에서 사본 경로를 확인한다. |
| `.dynote-sync/devices/….json`이 변경됐다고 나온다 | 이 파일에는 기기 이름과 등록 상태가 들어 있다. 노트와 관리 파일을 그대로 보존하고 아래 읽기 전용 명령으로 변경 내용을 확인한다. `M`과 `i/lf w/crlf`만으로 어떤 필드가 바뀌었는지 알 수 없다. |
| `Git 정보를 확인하지 못했습니다` 또는 `dubious ownership`이 뜬다 | **저장소 Git 원격**은 선택한 폴더에 기록된 Git 주소를 읽는 항목이다. 소유권 오류라면 보관함에서 Git Bash를 열고 `git status`를 실행한다. Git이 안내한 경로와 본인의 보관함이 같은지 확인한 뒤 그 폴더에 한해 안내를 적용한다. `D:\PrivateNote`와 네트워크 경로가 같은 폴더를 가리킬 수 있다. |
| 복제는 됐는데 업로드가 실패한다 | 설정의 저장소 주소·브랜치와 해당 계정의 브랜치 쓰기 권한을 확인한다. 일시 단절이었다면 연결 복구 후 **지금 동기화**를 누른다. `공통 Git 이력이 없습니다`가 계속되면 기존 노트를 보관하고 **기존 Git 저장소에서 가져오기**에서 별도의 빈 폴더를 고른다. 기존 폴더의 고유 문서는 새 보관함과 비교 후 옮긴다. |
| 수신 오류 직후 보이던 파일이 사라진다 | 열려 있는 편집 내용은 별도 사본으로 저장한다. 앱을 닫고 숨김 폴더 `.git`을 포함한 보관함 전체를 별도 위치에 복사한다. 같은 이름으로 새 파일을 생성하면 복구할 원본과 구분하기 어려워진다. 저장 위치의 쓰기·파일 교체 문제가 해소된 뒤 앱을 다시 열어 수신을 재개한다. |

관리 파일의 차이를 확인할 때 Windows 명령 프롬프트와 PowerShell에서 아래 두 줄을 쓸 수 있다. 두 번째 줄은 마지막 로컬 커밋과 비교하며 줄 끝의 CR 차이를 무시한다. 출력이 비었을 때는 첫 줄의 추적 상태도 함께 확인한다.

```text
git -C "D:\PrivateNote" status --short -- ".dynote-sync/devices"
git -C "D:\PrivateNote" diff --no-ext-diff --no-textconv --ignore-cr-at-eol HEAD -- ".dynote-sync/devices"
```

**관리 파일 때문에 계속 막히고 원격의 노트와 기기 기록이 정상인 경우**에는 기존 보관함을 보존한 채 작업을 재개할 수 있다. 열린 초안을 별도로 저장하고 기존 보관함에서 **이 기기 동기화 끄기**를 누른다. 같은 PC에서 **기존 Git 저장소에서 가져오기**로 별도의 빈 폴더를 연결한다. 새 보관함과 비교하면서 기존 폴더에만 있는 노트·첨부를 복사한다. 내용이 다른 동명 파일은 새 이름으로 보관한다. 이 절차를 재현했을 때 기기는 두 대로 유지됐고, 미전송 노트가 상대 PC에 도착했으며 기존 보관함의 원본도 남았다.

Cloud PC가 등록 목록에 없으면 Cloud PC의 개인 노트 Git 설정에서 **여러 PC에서 이어 쓰기**를 선택하고, 같은 저장소·브랜치와 이 기기 이름을 확인한 뒤 **이 설정으로 동기화**를 누른다. 두 PC가 등록되면 로컬 PC의 `File Storage`에 고유한 이름의 작은 `.md` 파일을 만든다. 로컬 PC, Cloud PC 순서로 **지금 동기화**를 누르고 Cloud PC에서 본문을 연다. Cloud PC에서 한 줄을 추가하고 반대 순서로 동기화한 뒤 로컬 PC에서 그 줄을 확인한다.

처음 보는 오류라면 파일이 **보낸 PC → 원격 저장소의 지정 브랜치 → 받는 PC** 중 어디까지 도착했는지 확인한다. 확인한 위치, 두 PC의 앱 버전, 오류 문구를 기록하면 다음 조사 지점을 정할 수 있다. 원인을 확인할 때까지 전송되지 않은 문서와 열린 초안을 별도로 보관한다.

기존 복구 경로도 확인했다. 같은 Markdown 문장을 두 기기에서 다르게 바꾸자 양쪽 원문이 버전으로 남았고, 선택한 내용이 두 보관함에 반영됐다. ZIP 우회 방법은 받은 ZIP과 압축을 푼 내부 파일을 각각 원본과 바이트 단위로 대조했다.

관련 자동 회귀 테스트 9개도 통과했다. 소유권 진단, 두 기기 등록·수신, Windows 방식 줄바꿈과 PDF·초안 보존, 파일 교체 중단 후 재개, 원격 이력 변경, 업로드 응답 유실, 기기 재등록을 포함한다. 하드링크 거부는 오류 주입 결과이며 실제 회사 NAS에서 이 오류가 발생했다는 증거는 없다.

다음 버전의 현장 확인에는 실제 Cloud PC의 매핑 드라이브와 네트워크 경로가 같은 보관함으로 인식되는지, 공유 폴더에서 파일을 열어 둔 채 수신과 재시작을 해도 원본 또는 복구 사본을 열 수 있는지, 네트워크 재연결 후 양방향 편집이 한 번씩만 반영되는지를 포함한다.
