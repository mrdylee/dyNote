# Dynote와 VS Code 연동 검토안

2026-10-20 · 검토 기준: Dynote v0.4.1 (`1bff9ac`).

**상태: 구현 전 제안.** v0.4.1에는 폰트 목록 수정만 배포했다. 이 문서의 연동 버튼·외부 변경 자동 반영·소스 위치 링크는 아직 구현하지 않았다.

## 추천 방향과 전제

Dynote 데스크톱 앱을 유지하면서 **같은 로컬 노트 폴더를 VS Code에서 열고, 저장된 파일 변경을 Dynote가 안전하게 반영하는 기능**을 먼저 추가한다. Mac과 Windows의 로컬 디스크 및 일반 VS Code를 우선 대상으로 가정한다. WSL·SSH·컨테이너·네트워크 드라이브는 경로와 파일 감시 방식이 달라 후속 검토 대상으로 둔다.

노트는 계속 일반 Markdown 파일로 저장한다. Dynote는 읽기·Live Preview·링크·그래프·Canvas·Bases를 담당하고, VS Code에서는 노트와 소스 코드를 편집하고 Git 변경을 검토한다. VS Code에서 저장하지 않은 편집 버퍼는 파일 감시로 읽을 수 없으므로 두 앱의 공동 실시간 편집을 약속하지 않는다.

## 대안 비교

| 방식 | 가능한 사용 흐름 | 개발 부담과 제한 | 판단 |
|---|---|---|---|
| 현재의 같은 폴더 + 수동 새로고침 | VS Code 저장 후 Dynote에서 문서 새로고침 | 추가 개발 없음. 새로고침마다 열린 탭 상태가 초기화되고 수동 조작 필요 | 지금 사용 가능 |
| 데스크톱 앱에 연결 기능 추가 | Dynote에서 VS Code 열기, 외부 저장 감지, 초안 충돌 안내 | 열기 버튼은 작고, 편집 상태를 보존하는 파일 반영 처리가 핵심 작업 | **우선 추천** |
| VS Code 전용 확장 | 사이드바·명령·웹뷰에서 Dynote 기능 사용 | Electron IPC·파일 접근을 확장 API로 옮기고 편집기·배포·수명 주기를 별도 관리해야 함 | VS Code 안에서 그래프·Canvas까지 써야 할 때 재검토 |

현재 목적에는 두 번째 방식으로도 문서와 코드 사이를 오가는 작업을 충분히 줄일 수 있다. 세 번째 방식은 “VS Code 내부에서 모든 작업”이 필수일 때 가치가 커진다. 이 판단은 현재 코드 구조에 근거한 설계 의견이다.

## 현재 구현에서 확인한 점

- `src/App.jsx`의 `reload()`는 `install(snapshot)`을 호출한다. `install()`은 활성 문서·열린 탭·저장 큐를 다시 만든다. 이를 파일 감시 이벤트마다 호출하면 편집 흐름이 끊기므로 재사용하면 안 된다.
- `src/saveQueue.mjs`는 문서별 미저장 초안과 저장 중 추가 편집을 관리한다. 새 외부 변경 처리도 이 큐와 기존 revision 값을 사용해야 한다.
- `core/vault.mjs`는 저장 전 파일 revision을 확인하고 임시 파일 작성 후 다시 확인한다. 외부 변경이 있으면 저장을 거절하지만 자동 병합은 하지 않는다. 두 프로세스 사이의 파일 잠금이나 원자적 비교 후 교체를 제공하는 것은 아니다.
- `electron/preload.cjs`에는 VS Code 전용 API나 보관함 변경 알림이 없다. `core/security.mjs`의 일반 외부 링크는 HTTP·HTTPS·mailto만 허용한다.
- Git 자동 백업은 앱이 열려 있을 때 지정 주기로 디스크 파일을 검사해 커밋·푸시한다. 따라서 VS Code에서 저장한 지원 파일도 다음 백업에 포함될 수 있다. 외부 변경을 즉시 상태 표시줄에 알리는 기능은 없다.
- Git은 수동 스테이징·진행 중 merge/rebase·다른 브랜치·갈라진 원격 이력을 거절한다. 자동 pull이나 충돌 해결은 하지 않는다. 노트 보관함은 독립적인 Git 저장소의 루트여야 한다.

## 권장 구현 순서

### 1. 현재 문서와 보관함을 VS Code로 열기

문서 메뉴에 **VS Code에서 열기**, 보관함 메뉴에 **보관함을 VS Code에서 열기**를 추가한다. 현재 문서를 열기 전 Dynote의 미저장 내용을 저장하고, 충돌 때문에 저장에 실패하면 기존 오류와 초안을 유지한다.

첫 구현은 VS Code가 공식 지원하는 `vscode://file/...` 링크를 Electron main에서 구성하는 방식이 단순하다. 사용자가 누른 전용 버튼만 이 동작을 실행한다. 일반 Markdown 링크 허용 목록에 모든 `vscode:` 주소를 추가하지 않는다.

- renderer는 보관함 ID와 상대 경로만 전달한다. main에서 현재 보관함 여부·지원 문서 종류·실제 경로·심볼릭 링크 이탈을 검증한다.
- main이 `file` 대상 주소를 만들고 경로의 공백·한글·`#`·`%` 등을 인코딩한다. 문서에서 받은 주소나 명령을 그대로 실행하지 않는다.
- VS Code 미설치·URL 연결 실패·Windows 길이 제한에는 안내와 “폴더 위치 보기”를 제공한다. 첫 버전에 별도 실행 파일 경로 설정이나 임의 명령 입력은 넣지 않는다.
- Canvas·Bases를 이 버튼으로 열면 VS Code에서는 JSON/YAML 원문을 편집한다. Dynote의 시각 편집기가 VS Code에 생기는 것은 아니다.

근거: VS Code는 파일·폴더·줄 위치 URL과 CLI를 제공한다. Electron은 OS의 URL 처리기를 호출할 수 있다. CLI는 후속 대안이며, macOS의 PATH 등록과 Windows 실행 파일 처리까지 추가 검증이 필요하다. [VS Code 문서](https://code.visualstudio.com/docs/configure/command-line#_opening-vs-code-with-urls), [Electron shell 문서](https://www.electronjs.org/docs/latest/api/shell).

### 2. 외부 변경 감지와 초안 보호

첫 자동 반영 범위는 Markdown과 첨부파일 목록이다. Canvas·Bases의 외부 변경은 알림 후 문서 단위 새로고침으로 시작한다. 시각 편집 중인 보드·표의 자동 병합은 별도 작업이다.

main에서 보관함 디렉터리 변경을 감시하고 이벤트를 짧게 묶어 변경 파일을 다시 읽는다. 파일 하나만 감시하면 임시 파일 교체 저장을 놓칠 수 있다. 알림 자체를 진실로 삼지 않고 실제 파일과 revision을 재확인한다. 파일명이 없는 이벤트·감시 오류·앱 복귀 시에는 제한된 재검색으로 보완한다. `.git`, 복구/휴지통, 임시 파일, 지원하지 않는 파일은 문서 갱신에서 제외한다. 보관함 교체·앱 종료 때 감시를 해제하고 오래된 보관함 알림을 버린다.

| 발생 상황 | Dynote의 제안 동작 |
|---|---|
| 변경된 Markdown에 로컬 초안 없음 | 해당 문서 내용·revision·검색/링크 자료를 갱신. 활성 탭과 가능한 커서·스크롤 위치 유지 |
| 같은 파일에 로컬 초안 또는 진행 중 저장 있음 | 자동 교체를 보류. 현재 초안을 유지하고 외부 변경 알림 표시 |
| 외부 내용과 로컬 초안이 완전히 같음 | 최신 revision을 채택하고 중복 저장·충돌 알림 방지 |
| 파일 삭제/이동 | 목록에 반영하되 열린 초안은 유지. 외부 이동은 삭제+생성으로 취급하고 기존 문서 링크를 추측해서 다시 쓰지 않음 |
| 이미지/PDF 교체 | 첨부 목록과 해당 미리보기 캐시 갱신 |
| Canvas/Base 외부 변경 | 변경 알림과 문서 단위 새로고침. 로컬 변경이 있으면 먼저 초안 보호 |
| Git 작업으로 다수 파일 변경 | 이벤트를 묶고 실제 상태를 재확인. 파일마다 전체 보관함을 다시 설치하지 않음 |

초안 충돌 시 첫 버전은 **초안을 별도 복구 사본으로 저장**, **외부 버전 다시 읽기**, **나중에 처리**를 제공한다. 별도 사본 저장 성공을 확인하기 전 초안을 지우지 않는다. 세 방향 병합과 자동 덮어쓰기는 후속 범위다. 외부 버전을 채택한 문서는 새 편집 기준으로 삼아 오래된 undo가 외부 변경 전체를 되돌리지 않도록 한다. 변경 없는 다른 문서의 편집 상태는 보존한다.

기존 `install()`과 별개로 변경 자료를 적용하는 경로가 필요하다. 저장 중 추가 타이핑, 자기 저장에서 발생한 이벤트, 보관함 교체가 겹치는 경우를 검증해야 한다. 원래 snapshot 전체 전달 구조이므로 큰 보관함의 인덱스 재계산 횟수를 측정하고, 이벤트마다 전체 재계산하는 방식은 피한다.

파일 감시는 OS와 저장 방식에 따라 이벤트가 누락될 수 있다. 수동 새로고침을 계속 제공하며 “항상 즉시 일치”를 보장하지 않는다. 실제 번들 Electron의 Node 버전에서 지원되는 API만 사용한다. [Node 파일 감시 제한](https://nodejs.org/api/fs.html#caveats).

### 3. 노트에서 코드 파일의 줄 위치로 이동

ATS/BMS 설계 노트에서 `src/bms.c`의 특정 줄을 열고 싶을 때 추가한다. 프로젝트 식별자·상대 경로·줄 번호를 노트에 보관하고, 기기별 코드 폴더 매핑은 로컬 설정에 둔다. Mac 절대 경로를 Windows에도 그대로 저장하지 않는다.

이 단계에는 별도의 링크 문법 결정과 범위 검증이 필요하다. 현재 문서 열기보다 먼저 구현하지 않는다. 코드 구조 변경 뒤 줄 번호는 달라질 수 있으므로 심볼 추적까지 지원한다고 표현하지 않는다.

## 사용할 때의 흐름

1. **문서와 코드 함께 작업:** 별도 노트 저장소와 코드 저장소를 VS Code의 다중 폴더 작업 공간에 추가한다. 노트에서 상세 설계를 쓰고 코드를 편집한다. Dynote에서는 문서 관계와 미리보기를 본다. 노트 자동 백업이 소스 코드까지 커밋하지 않도록 저장소를 분리한다.
2. **VS Code에서 노트 대량 수정:** Dynote 미저장 작업을 저장한 뒤 VS Code에서 검색·치환하고 저장한다. 현재 버전은 Dynote 수동 새로고침이 필요하다. 2단계 구현 후에는 깨끗한 Markdown에 변경이 자동 반영된다.
3. **다른 PC의 변경 가져오기:** Dynote 자동 Git 백업 끄기 → 로컬 저장 완료 확인 → VS Code/Git에서 pull·병합 및 충돌 해결 → Dynote 새로고침 및 내용 확인 → 자동 백업 재개. 자동 반영을 구현해도 Git 이력 통합은 이 흐름을 유지한다.
4. **양쪽에서 같은 문서 수정:** Dynote 초안과 디스크 버전을 모두 보존해 선택한다. VS Code의 미저장 버퍼까지 Dynote가 감지하거나 잠그지는 못한다.

## 구현 완료 판정 기준

- Mac와 실제 Windows에서 한글·공백·특수문자 경로의 문서와 폴더가 VS Code에서 정확하게 열린다. 미설치, 삭제 파일, 잘못된 보관함 ID와 경로 이탈은 실행 없이 처리한다.
- 실제 VS Code 저장 및 임시 파일 교체 저장이 Dynote에 반영된다. 일반 1,000문서 로컬 시험 보관함에서 저장 후 2초 이내 반영을 초기 목표로 측정하되 현재 성능 보장으로 쓰지 않는다.
- 양쪽 편집·700ms 자동 저장 타이머·저장 중 재입력·외부 삭제를 겹쳐 시험한다. 충돌하면 초안이 남고, 복구 사본은 원문 바이트를 보존한다.
- 변경 없는 탭·활성 문서·커서가 초기화되지 않는다. 외부 내용 반영만으로 다시 자동 저장되는 반복이 없다.
- Git checkout/pull의 다수 변경, 앱 포커스 복귀, 보관함 교체 후 오래된 이벤트를 검증한다. 감시 장애가 화면에 드러나고 수동 갱신이 작동한다.
- Git 백업과 외부 수정이 겹칠 때 상태가 정확하다. 초안 충돌 중에는 해당 미해결 상태를 알리고 백업을 일시 정지하는 정책을 적용한다. 사용자가 VS Code에서 수동 스테이징한 내용은 기존처럼 임의 커밋하지 않는다.

## 검토 결론

1단계는 작은 추가 작업이다. 2단계가 핵심이며 편집 상태와 충돌 처리가 제대로 동작해야 연동이라고 부를 수 있다. 3단계는 BMS/ATS 문서와 코드 연결이 실제로 필요할 때 이어간다. 전용 VS Code 확장은 이 흐름을 사용해 본 뒤, VS Code 안에서 그래프나 Canvas가 꼭 필요한지를 기준으로 결정한다.

문서 자체 검토: 현재/제안 구분, Mac·Windows 범위, WSL 제외, Git 자동 백업과 이력 통합의 구분, 초안 보호, 파일 감시 한계 및 검증 조건을 확인했다. 새로운 연동 코드는 이 검토에서 작성하지 않았다.
