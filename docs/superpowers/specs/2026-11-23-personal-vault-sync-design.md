# 여러 PC에서 이어 쓰는 개인노트

2026-11-23 · 설계 · 기준 소스 v0.23.15 (c3f5951)

## 사용자가 확인할 결과

Cloud PC에서 쓴 회의록이 Local PC의 열린 탭에 나타난다. Local에서 문장을 이어 쓰고 개인 보관함이나 그 안의 File Storage에 견적 파일을 복사하면 Cloud에서도 같은 파일을 열 수 있다. 각 기기에 독립된 로컬 복제본이 있고 원격 Git 브랜치 하나를 공유한다. 기기는 나중에 추가할 수 있고 다른 기기의 접속을 기다리지 않는다. 오프라인에서는 기기에 저장한 때와 원격에 반영된 때를 구분한다.

[두 PC 설계](2026-11-20-dual-pc-sync-design.md)의 초안 보호, Journal 처리, 경로 검사, 원격 이력 보호 조건을 이어받는다. 개인 보관함의 전송 주기, 기기 목록, 파일별 충돌 처리 및 복원은 이 문서를 따른다. 팀 공유와 기존 설치의 백업 정책은 별도의 설정이다. 신규 양방향 동기화는 개인 보관함에서 원격과 브랜치를 확인하고 켠다.

## 검토한 방법

| 방법 | 사용자에게 미치는 영향 |
|---|---|
| 기존 Dynote 저장·Git 처리에 양방향 동기화 추가 **(채택)** | 편집기, 스티키 노트, 수집기의 저장 시점을 함께 조정할 수 있다. 파일별 충돌 보존과 재시작 복구를 구현하고 시험해야 한다. |
| 독립 Git 폴더 동기화 엔진 연결 | 파일 감시와 주기 전송 구현을 재사용할 수 있다. Dynote 메모리에만 있는 초안과 디스크 교체 시점을 조정하는 통로가 여전히 필요하다. |
| 현행 백업과 수동 가져오기 | 사용자가 앞선 기기의 업로드와 내 기기의 가져오기를 직접 확인해야 한다. 두 기기의 이력이 갈라지면 앱 밖에서 통합해야 한다. |

참고한 동작은 Apple iCloud 문서의 버전 선택, GitNote의 창 복귀 시 수신, Git Sync의 백그라운드 폴더 감시다. 사용자는 Dynote 안에서 작업하고 전송에는 기존 Git 원격을 사용한다. [Apple 문서 충돌 처리](https://developer.apple.com/documentation/uikit/uidocument) · [GitNote](https://github.com/amaya382/vscode-gitnote) · [Git Sync](https://github.com/cognitoforms/git-sync)

## 기기와 커밋

설치별 난수 ID를 보관함 밖 앱 설정에 저장한다. 사용자는 Cloud PC 등 표시 이름을 정할 수 있다. 공유 저장소의 전용 경로 `.dynote-sync/devices/<id>.json`에 ID·이름·등록 상태를 기록한다. 등록·개명·해제 때만 갱신한다. 마지막으로 받아 본 활성 등록 파일 수를 ‘등록 기기 N대’로 표시한다. 이름이 같은 설치는 짧은 ID도 보여주며, 이름을 바꿔도 같은 기기로 센다. 등록 해제는 목록을 관리하는 동작이다. 접근 권한은 원격 Git 인증이 담당한다.

Git 작성자는 사람으로 유지한다. 자동 커밋에 전체 기기 ID와 당시의 이름을 기록한다. 외부 Git 커밋에는 확인 가능한 작성자를 표시한다. 변경 없이 확인만 하면 커밋은 0개다. 5분 배치라면 계속 편집하는 한 PC의 정기 편집 커밋은 시간당 최대 12개다. 창 이탈 시 대기분 전송, 등록, 병합, 충돌 해결은 별도의 커밋이 될 수 있다.

## 저장부터 상대 기기 화면까지

1. 편집은 기존 로컬 저장 큐에 맡긴다. 개인 보관함의 첫 대기 변경부터 5분 안에 변경분을 묶는다. 계속 타이핑해도 기한을 뒤로 밀지 않는다. 창 이탈·지금 동기화 때는 저장 가능한 대기분을 먼저 보낸다. 짧은 연속 이벤트는 보관함별 한 작업으로 합친다.
2. 창 복귀·재연결에는 즉시 원격을 확인한다. 앱이 열려 있으면 약 1분마다 짧은 무작위 지연을 두고 다시 확인한다. 원격 데스크톱 연결 전환이 창 이벤트를 만들지 않아도 주기 확인이 작동한다. 수신 확인 자체는 5분의 편집 배치 기한을 앞당기지 않는다. 원격 갱신과 로컬 작성이 겹치면 로컬 원문을 먼저 보호하고 통합한다.
3. Dynote에서 넣은 첨부는 기존 임시 파일 복사가 성공한 뒤 묶음에 추가한다. 탐색기·Finder에서 붙여넣은 파일도 폴더 감시와 재검사로 발견한다. 앱이 실제로 받은 복사 완료 신호와 단순 파일 생성 이벤트를 구분한다. 앱 밖의 느린 복사는 잠금·크기·수정 변화와 읽기 전후 파일 검사를 사용한다. 인식 가능한 ZIP 계열은 일관된 끝 구조도 확인한다. 임의 프로그램의 쓰기 종료를 파일 감시만으로 증명할 수 없으므로 불확실한 파일은 대기시키고, 나중에 바뀌면 다시 검사한다. 앱에서 파일과 함께 만든 노트 링크는 파일이 준비된 묶음에 실어 보낸다.
4. 원격과 로컬이 같으면 종료한다. 원격만 앞서면 안전하게 받는다. 로컬만 앞서면 올린다. 양측이 갈라졌으면 공통 원문·로컬·원격을 격리 공간에서 비교한다. 원격 재작성·삭제·무관한 이력, 직접 스테이징한 작업은 정상 경합과 구분해 해당 보관함에 이유를 표시한다. 실제 브랜치 갱신은 확인한 원격 커밋과 서버가 가진 커밋이 같고 결과가 그 후손일 때만 허용한다. 정상 경합이면 다시 받아 무작위 지연 후 재계산한다. 응답을 잃었으면 먼저 원격에 내 커밋이 도달했는지 확인한다.
5. 적용 직전 해당 파일 내용, 로컬 HEAD와 편집 세대 번호를 다시 확인한다. 적용과 저장이 경합하면 최신 입력을 초안으로 보존하고 다시 비교한다. 파일 교체 전 복구 가능한 로컬 상태를 남기고 재시작 때 미완료 작업을 재검사한다. 화면은 같은 보관함의 탭·목록만 갱신한다. 읽던 위치를 유지하고 오래 열려 있던 탭이 이전 본문을 다시 저장하는 일을 막는다.

## 파일별 충돌과 복원

| 파일 상태 | 결과 |
|---|---|
| 한쪽만 변경, 두 쪽의 결과가 동일 | 자동 적용. 동일 내용은 한 번만 기록한다. |
| Markdown의 겹치지 않는 수정 | Git 3방향 병합 후 두 내용을 반영한다. Journal 자동 블록·수집 세션에는 앞선 설계의 전용 규칙을 적용한다. |
| 같은 문장 수정, 같은 이름으로 서로 다른 파일을 추가 | 원본 경로에는 먼저 공개된 원격 버전을 표시하고 모든 후보를 보존한다. ‘버전 확인’을 열면 Markdown은 겹친 부분과 공통 원문을 비교할 수 있다. |
| ZIP·XLSX·PPTX·PDF 동시 변경 | 원본 바이트를 기기별로 열어보거나 내보낼 수 있게 보존한다. 사용자는 하나를 선택하거나 모두 유지하면서 사본 경로를 고른다. 두 파일이 정해질 때까지 기존 링크는 원본 경로를 가리킨다. |
| 삭제와 수정, 모호한 이동 | 삭제 의도와 수정본을 모두 기록한다. 파일이 이미 삭제됐다면 ‘검토할 파일’ 목록에서 수정본을 열 수 있다. 자동 재생성은 피한다. |

미해결 후보는 Git 트리의 전용 경로에 본문 바이트와 출처(원래 경로·원본 커밋·기기)를 함께 담는다. 각 변경 이벤트는 경로와 원본 커밋으로 식별하고 동일 바이트는 한 번만 보관한다. 병합 커밋에 양쪽 부모와 미해결 후보를 포함해 일반 Git으로도 도달할 수 있게 한다. 이로써 다른 노트의 변경도 같은 시점에 전송할 수 있다. 세 번째 PC가 오프라인 수정본을 보내면 같은 파일의 후보 목록에 추가한다. 선택 결과는 사용자가 본 후보 집합에만 적용한다. 해결 도중 도착한 새 버전이나 다른 기기의 별도 선택은 보존하고 다시 보여준다. ‘모두 유지’는 Windows·macOS에서 기존 파일명과 충돌하지 않는 경로를 미리 보여준다.

**재검토에서 발견한 경우.** 원격에 ‘2시’가 표시되고 ‘3시’가 검토 중일 때, ‘2시’를 이미 받아 둔 다른 PC에서 ‘4시’로 고칠 수 있다. Git은 이 경우 정상 병합으로 ‘4시’를 채택할 수 있다. 따라서 병합 성공 여부와 별도로 이미 검토 중인 경로에 대한 새 쓰기·삭제를 찾고, 명시적인 해결 요청이 없으면 기존 표시본과 새 후보를 함께 보존한다. fast-forward가 가능한 전송도 같은 검사를 거친다. 기존 일반 Git 앱에서 직접 게시한 변경은 다음 Dynote 동기화 시 과거 이력과 검토 기록에서 후보를 복구한다. Dynote 밖에서 직접 게시한 시점의 원격 표시본까지 제어할 수는 없다.

기본 화면은 ‘기기에 저장됨’, ‘동기화됨’, ‘버전 확인 N개’만 필요할 때 표시한다. 버전 기록은 문서 경로로 먼저 거른 뒤 날짜·기기·내용 미리보기를 제공한다. 전체 월의 최신 1,000건 안에서 파일을 뒤지는 방식을 피하고 이전 이력을 페이지로 읽는다. 해당 파일의 이전 내용을 선택하면 현재 내용도 보존하고 새 변경으로 기록한다. 다음 동기화에서 다른 PC에도 복원 결과가 전달된다. 기존 보관함 전체 복원 메뉴와 구분한다.

## 파일 범위와 저장소 경계

기존 개인노트 지원 형식에 ZIP을 추가한다. ZIP은 그대로 전송·복원하고 자동으로 풀지 않는다. 드롭, 탐색기 복사, Git 전송, 개별 복원을 모두 시험한다. 기존 복원에는 파일당 25 MiB와 전체 스냅샷 512 MiB 제한이 있다. 새 파일별 처리에서도 지원 크기와 초과 시 이유를 표시하고, 로컬에만 남은 파일이 있으면 보관함 전체에 ‘동기화됨’을 표시하지 않는다. 저장소의 개별 첨부를 선택하는 데 전체 스냅샷을 읽을 필요는 없다. 이 단계의 인수 대상은 일반 Git에 저장한 파일이다.

전용 메타데이터는 사용자 문서 경로 검사와 분리한다. 스키마, 경로, 모드, 크기를 검증하고 허용된 기기·충돌 레코드만 취급한다. 임의 숨김 파일, 링크, Office 임시 파일, 보관함 밖 링크 대상, 인증 정보는 자동 게시 대상에서 제외한다. 이미 추적된 지원 밖 파일이나 경로 충돌은 기존 검토 규칙을 따른다. 기존 개인용 백업·로컬 전용·팀 보관함까지 양방향 모드로 바꾸지 않는다. 새 모드에서 ZIP을 처음 게시하기 전에 기존 로컬 ZIP도 전송 대상이라는 점과 파일 목록을 보여준다.

## 완료를 판단할 시험

- 같은 기준에서 독립된 Git 복제본 두 개와 추가 오프라인 기기를 사용한다. Cloud에서 Markdown 작성 → Local에서 열린 탭으로 수신 → 문장 추가와 첨부 → Cloud에서 확인한다. 모든 기기의 원문·첨부 해시·최종 브랜치가 같아지고, 반복 확인에서는 커밋이 늘지 않아야 한다.
- 같은 문장과 같은 Excel을 세 기기에서 수정하고 정상 노트도 하나 보낸다. 모든 후보 바이트와 삭제 의도가 남고 정상 노트는 먼저 도착해야 한다. 두 기기의 동시 해결과 재시작에도 보관함에 충돌 표식이나 중복 사본이 생기지 않아야 한다.
- 창 이벤트가 없는 RDP 전환, 수신 중 타이핑, 탐색기 복사 중 연결 끊김, Push 응답 유실, 여러 번의 경합, 외부 브랜치 되감기와 이름 대소문자 충돌을 각각 재현한다. 파일·초안·커밋 보존과 재접속 후 상태를 확인한다.
- 개인 공간에서 등록·개명·해제, 오프라인 재접속, 같은 이름 두 대, 팀 공간 격리를 확인한다. 파일 하나를 복원한 뒤 다른 파일의 해시는 같고, 복원 직전 버전도 선택 가능해야 한다.
- 실제 Windows Cloud PC와 Local PC에서 창을 계속 열어 둔 채 드래그와 탐색기 붙여넣기, 긴 한글 파일명, Office 열린 파일을 확인한다. Git 복제본 시험과 실제 사용 환경의 합격 여부는 따로 기록한다.
